# Persistent Bedrock Chat Retry Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep a manager chat turn pending across retryable Bedrock failures until a grounded Bedrock answer succeeds or the manager cancels/leaves.

**Architecture:** Every Agent API attempt remains bounded and returns a typed safe failure containing `error_code`, `correlation_id`, and `retryable`. The browser owns one cancellable retry loop per turn, uses capped exponential backoff with jitter, preserves the same question and structured context, and renders only the eventual Bedrock answer.

**Tech Stack:** FastAPI, Python, JavaScript, Node-based UI tests, pytest.

## Global Constraints

- Every successful user-visible chat response is generated by AWS Bedrock.
- No deterministic final chat-text fallback is allowed.
- Only transient Bedrock timeout, throttling, temporary 5xx, and open-circuit failures persistently retry.
- Authentication, authorization, validation, grounding, malformed evidence, and programming errors terminate safely.
- Jira mutations are outside this retry mechanism.
- One pending retry loop exists per chat turn and can be cancelled.
