# Persistent Bedrock chat design

## Goal

Transient Amazon Bedrock failures must not end a manager's chat turn with a
temporary-unavailable message. The browser continues waiting and retrying until
Bedrock returns a grounded answer or the manager explicitly cancels or leaves
the page.

## Selected approach

Use client-managed persistent retries rather than one indefinitely open HTTP
request. Each individual Agent API request keeps its existing bounded Bedrock
attempt timeout, retry budget, grounding checks, and correlation diagnostics.
When the API reports a retryable Bedrock timeout, throttling response, temporary
5xx, or open circuit, the UI keeps the chat turn pending, displays a
`Bedrock is still working...` status, waits with capped exponential backoff and
jitter, and resubmits the same question and structured conversation context.

The pending turn has a stable client request ID while every API attempt retains
its own correlation ID for diagnostics. Only one retry loop may exist for a
chat turn. A new question, Clear, project change, page departure, or an explicit
Cancel action aborts it.

## Boundaries

- Every successful user-visible answer remains generated by Bedrock and must
  pass the existing grounding validation.
- Deterministic fallback prose is prohibited.
- Authentication, authorization, validation, grounding, malformed evidence,
  and programming errors are terminal and shown as safe actionable errors;
  they are not retried indefinitely.
- Jira mutations retain their existing bounded, approval-controlled behavior
  and are never retried by this mechanism.
- Per-attempt timeouts and circuit breakers remain mandatory. The persistence
  applies to the browser chat turn, not to a single unbounded network request.

## Tests and acceptance

Tests first prove that retryable Bedrock failures keep one pending turn, do not
show the temporary-unavailable answer, preserve the question/context, apply
capped backoff, and eventually render the first grounded Bedrock success. Tests
also prove cancellation, single-loop enforcement, project-change cancellation,
and immediate termination for nonretryable errors.

The acceptance scenario makes multiple mocked Bedrock attempts fail before a
successful answer. The manager sees a working status followed by the Bedrock
answer, without manually resubmitting the question.
